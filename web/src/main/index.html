SolarNode Filter Simulator
The datum to run through the filters: a JSON object, or an array of objects, in the SolarNode datum format. A datum without a created date gets one, a second after the datum before it.

Datum sources are the node's simulated datum sources, which the simulation polls on their schedules, from the first datum, or else the Environment tab's Start Date, until it ends. The Datum Queue processes the datum they return, like the input datum. Operational Mode Invokers poll them on schedules of their own while their modes are active.

    Datum in the node's datum history when the run starts, which expression functions like latest() and offset() read. SolarNode keeps the latest 5 datum of each source.
    Datum from before the filters were applied, which the unfiltered*() functions read.
    The node ID of the datum the Execution Flow downloads as CSV. It is used only for those downloads.
    The time zone the Execution Flow shows dates in, and of the Start Date. Blank for the simulator's time zone, UTC. The simulation itself runs in the simulator's time zone: cron schedules, tariff schedules, and expression date functions like today() use it.
    The date of the first datum without a created date, and the start of a run without datum, which only polls the datum sources, in the Time Zone. Blank for now.
    How long the simulated clock keeps running after the last datum, so scheduled tasks, like the Timeout filter's, can run, and the datum sources are polled. Without datum, this is the length of the run. Seconds, like 90, or a duration, like 15m, 24h, 7d, or PT24H.
    The most datum a run processes, including the datum the filters generate and the datum sources' polls. Raise it for long runs, like a day of polls; the simulator allows up to 100,000 by default. A run with more than 200 datum shows them as a list.
    name = value lines, like the files in a node's conf/placeholders.d. Settings use them like /meter/{siteName}, and expressions as parameters.
    The modes active when the run starts, separated by commas.
    Node Location
    The node's location: latitude and longitude in decimal degrees, and elevation in meters. Filters like the POA Calculator can use it.
    Local State CSV, as SolarNode exports it. Blank Created and Modified dates default to the first datum's date.
    seconds
    How often the node's Instruction Execution Job runs the instructions waiting for it, like Control Conductor tasks, aligned to the minute: 10 runs them at seconds 0, 10, 20, and so on of each minute, like a node.
    Programs on this computer that filters may run, one full path per line, like the POA Calculator filter's Command. Allow only programs you trust.
    The node's metadata, which the Node Metadata Service provides: a JSON object with m, pm, and t properties. Expressions read it with functions like metadataAtPath('/pm/…').

    Datum Metadata

    The metadata of datum streams, by source ID. Expressions read it with functions like meta(sourceId).

    User Metadata Services

    User Metadata Services provide metadata from the SolarNetwork user account. Filters find one by its Service Name, like the Tariff filter's Metadata Service setting.

    Controls are the node's simulated controls, which filters like the Control Updater set. A control can publish a datum of its value, which the Datum Queue then processes.

    Control Conductors

    A Control Conductor runs its tasks when an OrchestrateControls instruction, such as an Instructor filter's, names it in its service parameter: each task sets a control at a time offset from the instruction's date parameter, or else from when the instruction runs.

    External Settings

    You can upload additional SolarNode settings CSV files to add those settings to the simulation. They will not be included in the settings export.

    These are like the auto settings files that SolarNode packages install, such as the Main filter chain of the solarnode-config-datumfilters package. They apply before the simulation's own settings, in file name order, and the first file with a setting wins. A setting in the simulation overrides the same setting in these files.

    File Setting Count Actions

    Import Settings

    Add the settings in to the simulation, or replace the simulation's settings with them?

    Add
    Keep the simulation's filters, and add the file's settings. A setting in the file replaces the same setting in the simulation, as when SolarNode imports a settings file.
    Replace
    Remove the simulation's filters, and use only the file's.

    The file's controls and Control Conductors go to the Controls tab: Add adds them, replacing those with the same control ID or Service Name, and Replace replaces them. You can undo either one with Ctrl+Z, except for the Controls tab.

    Save Simulation

    Enter a file name, without / or \.

    The simulation keeps this name, for the next time you save it. Your browser saves the file in its downloads folder, unless it asks where.

    Capture from SolarNode

    Record the datum a SolarNode captures, as they arrive, as input datum for the simulation. The simulator logs in to the node and receives each datum its Datum Queue gets, before the node's filters run.

    The login you use for the node's web app. The simulator does not save the password.
    Optional patterns of the source IDs to capture, separated by commas, like /meter/**, /inv/*; blank for every source. The datum that the node's own filters make, like the Split filter's, are captured too, so leave them out if the simulation makes them.
